1.  **`HOTSPOT_PENALTY_FACTOR`**: Increased from `100.0` to `150.0`. This makes the quadratic penalty for exceeding the critical utilization threshold significantly stronger, further discouraging placements that create or exacerbate resource bottlenecks on local machines.
2.  **`CAPACITY_PRESERVATION_PENALTY_FACTOR`**: Increased from `50.0` to `75.0`. This boosts the penalty for consuming capacity that falls below the `SAFE_RESERVE_THRESHOLD`, enhancing the scheduler's effort to maintain a buffer for future, potentially high-priority, jobs or to improve resilience during failures.
3.  **`HOTSPOT_LOOKAHEAD_WINDOW`**: Extended from `6` to `8` hours. A longer lookahead window for hotspot detection allows the scheduler to anticipate and avoid future congestion more proactively.
4.  **`CAPACITY_LOOKAHEAD_WINDOW`**: Extended from `12` to `16` hours. A longer lookahead for capacity preservation ensures that decisions consider the impact on resource availability further into the future, which is especially beneficial in scenarios with fluctuating capacity due to failures.

These changes aim to improve load balancing, resource resilience, and proactive avoidance of problematic placements.
</DESCRIPTION>

refine_local_search_iterative_window
</NAME>

<DESCRIPTION>
This edit refines the `find_best_placement` method's local search strategy. The current implementation uses a fixed `current_search_limit` initially derived from `self.urgency.search_horizon` and expands it `max_search_iterations` times.

The proposed change:
1.  **Initial Search Window**: Instead of starting the `current_search_limit` with the full `self.urgency.search_horizon`, it initializes with a tighter window: `self.earliest_start + max(self.op.duration * 2, self.inst.time_horizon // 6)`. This means the scheduler first attempts to find a slot very close to the earliest possible start time, reflecting a preference for immediate execution. This prioritizes efficiency and aims to reduce procrastination.
2.  **Iterative Expansion**: If no satisfactory local placement is found within this initial window (or if the best local score is still not competitive with the cloud benchmark), the search window is expanded. The increment for expansion is `self.inst.time_horizon // 4`, and it now explicitly caps the `current_search_limit` at `self.earliest_start + self.urgency.search_horizon` to ensure the overall search does not exceed the maximum horizon derived from the job's urgency profile.
3.  **Iteration Limit and Max Horizon**: `max_search_iterations` is adjusted to `4` (from `3`) to allow for slightly more granular expansions, and the upper bound of the search (`max_total_search_end`) is explicitly introduced to ensure the iterative expansion does not run indefinitely beyond the intended job-specific search horizon.

This strategy balances searching for immediate, low-cost slots with a controlled expansion to find a viable placement, improving search efficiency and resource utilization while respecting urgency.
</DESCRIPTION>
