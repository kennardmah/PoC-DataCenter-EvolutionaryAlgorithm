<DESCRIPTION>
This change introduces a "Capacity Tightness Penalty" to the operation scoring function. This new penalty is designed to be predictive and avoid creating "hotspots" where local server capacity is nearly exhausted.

The key ideas are:
1.  **Hotspot Identification**: The penalty only triggers if scheduling an operation would push a server's utilization above a high threshold (85%). This avoids penalizing placements on moderately busy servers.
2.  **Non-Linear Scaling**: The penalty increases quadratically as utilization approaches 100%. This provides a gentle nudge away from busy servers but a strong deterrent from creating a complete bottleneck that would force later jobs to the cloud.
3.  **Urgency-Aware**: The penalty is scaled by the job's priority multiplier. This makes the scheduler more careful about consuming the last available capacity slots, effectively preserving them for potentially more critical jobs that may arrive in the future.

This heuristic makes the scheduler more forward-looking. Instead of just reacting to the current average load, it actively penalizes decisions that would severely constrain future scheduling options. This is crucial for maintaining flexibility and resilience, especially in the high-contention earthquake scenario where local capacity is scarce.
</DESCRIPTION>

                used = self.capacity_usage.get(server_id, {}).get(t, 0)
                available = get_available_capacity(self.inst, server_id, t)

                if available > 0:
                    util_after_placement = (used + op.capacity_required) / available
                    if util_after_placement > self.critical_utilization_threshold:
                        # Non-linear penalty that grows quadratically as we approach 100% utilization
                        excess_util = util_after_placement - self.critical_utilization_threshold
                        # Normalize excess to be in [0, 1] range for the penalty calculation
                        normalized_excess = excess_util / (1.0 - self.critical_utilization_threshold)
                        # We use max to capture the worst bottleneck point during the operation's timespan
                        max_penalty_contribution = max(max_penalty_contribution, normalized_excess**2)
