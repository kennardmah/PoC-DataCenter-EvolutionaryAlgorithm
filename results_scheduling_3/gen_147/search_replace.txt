type_specific_system_load
</NAME>

<DESCRIPTION>
The original algorithm calculated a single system-wide load across all local machine types. This is inaccurate, as the contention a job faces is specific to the machine types its operations require. This change corrects this flaw by:
1. Identifying the unique set of server types required by the job being scheduled.
2. Calculating the average utilization for each of these specific server types over a lookahead window.
3. Averaging these type-specific loads to produce a single, more relevant `current_system_load` metric.
This improved metric provides a much more accurate input to the `JobUrgencyProfile`, leading to more intelligent decisions about cloud aggressiveness. For instance, the scheduler will now correctly recognize that the system is not congested for a GPU job even if the CPU servers are busy. The lookahead window is also increased from 6 to 12 hours for a more stable prediction.
</DESCRIPTION>

refined_slack_preservation
</NAME>

<DESCRIPTION>
The previous implementation of the "slack preservation" penalty, designed to prevent early operations from consuming all the slack needed for later ones, used a complex and potentially unstable exponential function. This change refactors this heuristic for better stability and predictability:
1. **Simplified Buffer Calculation:** The `critical_slack_buffer` is now calculated with a more intuitive formula: `remaining_duration * 1.25 + num_remaining_ops`, which represents a 25% time buffer plus a 1-hour-per-operation allowance for scheduling friction.
2. **Quadratic Penalty:** The volatile exponential penalty is replaced with a more stable quadratic penalty (`slack_shortfall ** 2`). This penalizes eating into the buffer at an increasing rate without the risk of explosive, unpredictable scores.
3. **Urgency Scaling:** The penalty's magnitude is scaled by the job's `delay_weight` and its dynamic `procrastination_penalty_multiplier`. This ensures the heuristic applies the most pressure to urgent, high-value jobs where preserving future flexibility is most critical. This change makes the decision-making process more robust against consuming future slack.
</DESCRIPTION>
