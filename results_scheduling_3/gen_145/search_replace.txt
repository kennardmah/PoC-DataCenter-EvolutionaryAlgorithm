<consistent_priority_maps_and_advanced_load_penalty>
This edit refactors the `JobScheduler` to implement a more sophisticated, non-linear load-balancing penalty, as inspired by recommendation #1, and ensures consistent priority key mapping.

**Key Changes:**
1.  **Consistent Priority Maps:** The priority mapping dictionaries (`priority_base_horizon`, `priority_procrastination_multiplier`, `cloud_aggressiveness_threshold`, `priority_load_multiplier`) have been updated to use consistent, capitalized keys (e.g., "Emergency", "Urgent", "High", "Medium", "Low") to match the `Job.priority` attribute directly. This resolves a potential inconsistency and improves readability. The values for `cloud_aggressiveness_threshold` are also slightly adjusted to better reflect the intent of favoring local for higher priority jobs (tolerating higher relative cost for local).
2.  **Advanced Load-Balancing Penalty Parameters:** New parameters (`high_utilization_threshold`, `critical_capacity_buffer_ratio`, `cubic_penalty_scale`, `buffer_penalty_scale`) are introduced in `JobScheduler.__init__` to control the new penalty behavior.
3.  **Non-Linear Load-Balancing Penalty Logic:** The `_calculate_operation_score` method's `load_penalty` calculation is significantly enhanced.
    *   **Predictive Lookahead:** The load analysis now considers the time window from the operation's `start_time` up to `start_time + op.duration * 3` (operation duration + 2x duration lookahead) to predict future congestion.
    *   **Non-Linear High Utilization Penalty:** A cubic penalty is applied if the *prospective utilization* (including the current operation) at any point in the lookahead window exceeds `high_utilization_threshold` (e.g., 85%). This dramatically penalizes placements that push a server close to its limits.
    *   **Critical Capacity Buffer Penalty:** A linear penalty is introduced if the `remaining_capacity` (after placing the operation) falls below a `critical_capacity_buffer_ratio` (e.g., 10%) of the server's *current available capacity* at any point in the lookahead. This incentivizes maintaining a minimum operational buffer for resilience.
    *   **Robustness for Zero Capacity:** An extremely high penalty is added if an operation is attempted on a server with zero available capacity after the proposed placement.
    *   The `load_penalty_factor` and `priority_load_multiplier` are now applied to scale these non-linear penalties, allowing for more granular control over how load impacts the score based on job priority.

These changes aim to improve performance by proactively managing local server congestion and reserving capacity buffers, especially critical during emergency scenarios, while still balancing cloud vs. local costs based on job urgency. The consistency in priority mapping reduces potential errors and improves maintainability.
