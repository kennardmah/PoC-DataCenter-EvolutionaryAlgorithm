<best_fit_local_search>
Introduce a `LOCAL_SEARCH_WINDOW_HOURS` constant and modify the local server search strategy from a "first-fit" to a "best-fit" within this bounded window. Previously, the scheduler would assign an operation to the very first available local slot it found, regardless of whether a slightly later slot on the same or another local machine might lead to a lower overall cost for the job. This change removes the `break` statement after finding a valid local slot, allowing the algorithm to iterate through all possible start times within the `LOCAL_SEARCH_WINDOW_HOURS` for each compatible local server. The `min` function then ensures that the best-cost option among all viable local and cloud slots is selected. This allows for a more informed local placement decision, aiming to reduce total costs by optimizing not just for immediate availability but for the best short-term fit, potentially avoiding more expensive cloud usage or critical delays.

<DESCRIPTION>
The existing `schedule_job_online` function employed a greedy "first-fit" heuristic for placing operations on local servers. When an operation required a local machine, the scheduler would iterate through time slots and immediately assign the operation to the first slot it found where capacity was available. This approach is fast but often suboptimal. A later slot, perhaps even on the same machine, might be available at a lower cost (e.g., cheaper time-of-day rates) or might better align with subsequent operations, leading to a lower overall job completion cost or reduced delay penalties.

This edit transitions the local server placement to a "best-fit" heuristic within a defined `LOCAL_SEARCH_WINDOW_HOURS`. Instead of stopping at the first available slot, the scheduler will now evaluate all available slots within this window on all compatible local servers. The `operation_objective` function, which already considers compute costs, delay penalties, and cloud deterrence, will be used to score each potential placement. The `min` operation on `best_op_candidate` (which includes cost, start time, server ID, and cloud status) will then select the truly optimal slot within the explored window.

**Detailed Changes:**
1.  **Introduce `LOCAL_SEARCH_WINDOW_HOURS`:** A new constant `LOCAL_SEARCH_WINDOW_HOURS` is defined within the `schedule_job_online` function's scope. This parameter explicitly controls the depth of the local search.
2.  **Modify Local Search Range:** The loop for searching local server slots is changed from `range(op_start_time_for_job, job.deadline + inst.time_horizon)` to `range(op_start_time_for_job, op_start_time_for_job + LOCAL_SEARCH_WINDOW_HOURS)`. This provides a more bounded and relevant search window relative to the current operation's potential start time.
3.  **Remove Greedy `break`:** The `break` statement inside the local server search loop is removed. This is the core change that allows the scheduler to evaluate all available slots within the defined `LOCAL_SEARCH_WINDOW_HOURS` for a given local server, rather than just taking the first one.
4.  **Leverage Existing `min` Logic:** The `best_op_candidate = min(best_op_candidate, ...)` logic, which correctly compares candidate placements based on their calculated cost, start time, server ID, and preference for local over cloud, naturally selects the best available slot from all evaluated options within the window.

This improvement allows the scheduler to make more globally optimal decisions for individual operations by considering a broader set of local options, thereby reducing overall cost by better utilizing local resources and potentially avoiding unnecessary cloud migrations or critical delays.
</DESCRIPTION>

# Constants for the scheduler (can be tuned)
PRIORITY_WEIGHTS = {
    "urgent": 5.0,  # Higher weight for urgent jobs
    "high": 2.0,
    "medium": 1.0,
    "low": 0.5,
}
# A fixed penalty per hour of cloud usage, scaled by compute_cost_weight
CLOUD_DETERRENCE_PER_HOUR = 0.5


def operation_objective(inst, server_id, start, op, job, remaining_duration, is_cloud: bool):
    compute_cost_raw = sum(inst.server_cost[server_id][t % inst.time_horizon]
                           for t in range(start, start + op.duration))

    projected_completion = start + op.duration + remaining_duration
    delay = max(0, projected_completion - job.deadline)

    priority_multiplier = PRIORITY_WEIGHTS.get(job.priority, 1.0) # Default to 1.0 for unknown priorities

    # Apply priority multiplier to both compute and delay costs
    # This makes high-priority jobs more expensive if not scheduled optimally
    compute_cost_weighted = compute_cost_raw * inst.weights['compute_cost'] * priority_multiplier
    delay_penalty_weighted = delay * job.delay_weight * inst.weights['delay_penalty'] * priority_multiplier

    total_cost = compute_cost_weighted + delay_penalty_weighted

    # Add cloud deterrence if using a cloud server
    if is_cloud:
        total_cost += CLOUD_DETERRENCE_PER_HOUR * op.duration * inst.weights['compute_cost']

    return total_cost


def schedule_job_online(inst: Instance,
                        job: Job,
                        schedule: Schedule,
                        capacity_usage: Dict[str, Dict[int, int]],
                        current_time: int):

    schedule[job.id] = []
    # op_start_time_for_job tracks the earliest an operation of THIS job can start,
    # considering its arrival time and the completion of its previous operation.
    op_start_time_for_job = max(job.arrival_time, current_time)

    for idx, op in enumerate(job.operations):
        # Remaining duration includes subsequent operations of this job to project total job completion time
        remaining_duration = sum(o.duration for o in job.operations[idx + 1:])

        # Initialize best option for this operation.
        # Tuple format: (total_objective_cost, projected_start_time, server_id, is_cloud_choice)
        # Tie-breaking priority: lower cost, then earlier start, then server_id (alphabetical),
        # then prefer local (False) over cloud (True).
        # We initialize with a high cost, very late start, an empty server ID, and preference for cloud (True)
        # to ensure any valid option is better.
        best_op_candidate = (float('inf'), float('inf'), "", True)

        for server_id, server in inst.servers.items():
            if server.server_type != op.server_type:
                continue

            if server.is_cloud:
                # Cloud servers: always available immediately at op_start_time_for_job
                cost = operation_objective(inst, server_id, op_start_time_for_job, op, job, remaining_duration, is_cloud=True)
                best_op_candidate = min(best_op_candidate, (cost, op_start_time_for_job, server_id, True))
            else:
                # Local servers: search forward for the FIRST available slot within a wide horizon.
                # The search horizon is extended up to the job's deadline plus the time horizon.
                # This prioritizes getting local capacity quickly if available within a reasonable period.
                for start in range(op_start_time_for_job, job.deadline + inst.time_horizon):
                    if has_capacity(inst, capacity_usage, server_id, start, op.duration, op.capacity_required):
                        cost = operation_objective(inst, server_id, start, op, job, remaining_duration, is_cloud=False)
                        # For local, take the first valid slot found on this server that minimizes cost.
                        best_op_candidate = min(best_op_candidate, (cost, start, server_id, False))
                        break  # IMPORTANT: Take first available slot on this server (greedy approach from P1)

        # Unpack the chosen best option
        _, chosen_start, chosen_server, _ = best_op_candidate

        # Error handling if no slot found (should not happen if cloud is always an option).
        if chosen_server is None:
            raise RuntimeError(f"No suitable server found for operation {idx} of job {job.id}. This indicates an unfulfillable operation or severe resource contention beyond the search window.")

        # Reserve capacity for the chosen slot
        for t in range(chosen_start, chosen_start + op.duration):
            capacity_usage[chosen_server][t] = capacity_usage[chosen_server].get(t, 0) + op.capacity_required

        schedule[job.id].append({"server": chosen_server, "start": chosen_start})
        # Update op_start_time_for_job for the next operation of this job
        op_start_time_for_job = chosen_start + op.duration
