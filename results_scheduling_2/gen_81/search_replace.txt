<add_future_compute_cost_lookahead>
This enhancement integrates a limited lookahead mechanism into the operation objective function. Previously, when evaluating a potential slot for an operation, the system only considered the current operation's compute cost and the overall job's delay penalty based on projected completion. This modification extends the heuristic to also estimate the *future compute costs* for all subsequent operations within the same job.

The `_calculate_placement_score` helper function is updated to:
1.  Take the current operation's index (`_op_idx`) and the full list of `_job_operations` as parameters.
2.  Pre-calculate `min_hourly_cost_by_type` for all local servers once per job scheduling to efficiently estimate future costs.
3.  For each potential placement, it now calculates `projected_future_compute_cost` by summing the estimated minimum cost for each remaining operation. This is done by looking up the minimum hourly cost for the required server type from local machines or using a high fallback cost (e.g., cloud deterrence base) if no local option is available.
4.  The `projected_future_compute_cost` is then added to the `op_compute_cost` before multiplying by `inst.weights['compute_cost']`, ensuring that decisions consider the total expected compute expenditure for the entire job.

This change aims to prevent scenarios where an operation is placed on a cheap local machine that then blocks subsequent operations, forcing them onto expensive cloud resources later. By looking ahead at the full job's compute cost, the scheduler can make more globally optimal decisions, balancing immediate cost savings against future expenditure and deadline adherence.
