<DESCRIPTION>
This edit introduces a dynamic local search window for scheduling operations on local machines, based on job priority.

**Motivation:**
The previous implementation used a fixed `MAX_LOCAL_SEARCH_WINDOW` for all jobs, which might not be optimal for balancing urgency and cost.
-   **High-priority (Emergency/High) jobs:** For these jobs, it's crucial to minimize delay. A shorter search window for local machines encourages the scheduler to quickly determine if an immediate or near-term local slot is available. If not, it forces an earlier consideration of potentially more expensive but immediately available cloud resources, reducing overall job delay. This aligns with the "local search window for on-premise machines" recommendation, making it adaptive.
-   **Low-priority (Medium/Low) jobs:** These jobs have more flexibility regarding their completion time. A longer search window allows the scheduler to explore further into the future for cheaper local slots, potentially waiting out peak times or capacity shortages, thus reducing compute costs without significantly impacting critical deadlines.

**Changes Proposed:**
1.  **Introduce `BASE_LOCAL_SEARCH_WINDOW_HOURS`**: A base duration for the local machine search window.
2.  **Introduce `LOCAL_SEARCH_WINDOW_PRIORITY_FACTOR`**: A dictionary that maps job priorities to multipliers for the base search window. Emergency jobs get a factor less than 1 (shorter window), while low-priority jobs get a factor greater than 1 (longer window).
3.  **Calculate `actual_local_search_window`**: This dynamically determined window will be used for `search_end_time` when evaluating local machine slots, replacing the fixed `MAX_LOCAL_SEARCH_WINDOW`. This makes the heuristic more responsive to job urgency, improving the balance between delay penalties and compute costs.

This change aims to improve the combined score by making more intelligent trade-offs in local machine usage based on job priority, potentially leading to better critical job completion times (by moving them to cloud faster if local isn't immediately optimal) and lower costs for less critical jobs (by allowing them to search for better local slots).
</DESCRIPTION>
