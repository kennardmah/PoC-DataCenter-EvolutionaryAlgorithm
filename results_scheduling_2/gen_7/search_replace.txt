<DESCRIPTION>
The current heuristic for local machines searches for the first available slot up to `job.deadline + inst.time_horizon`. This window can be extremely large, potentially causing the scheduler to commit to a very distant local slot even if an immediate (but slightly more expensive) cloud option is available. In an online, dynamic environment with high penalties for delay, committing too far into the future to save compute cost for a single operation might be suboptimal for the overall job completion or other urgent jobs.

This edit introduces a `MAX_LOCAL_SEARCH_WINDOW_HOURS` constant (set to 48 hours heuristically). For local machines, the search for the *first* available slot is now limited to `current_start + MAX_LOCAL_SEARCH_WINDOW_HOURS`. This means if a local machine doesn't have an available slot within this reasonable lookahead window, the cloud option (which is always available immediately) will likely be preferred due to its immediate start, balancing compute cost against the implicit penalty of pushing the current operation far into the future. This change helps manage the trade-off between local cost and job urgency/throughput, especially for jobs with distant deadlines, by making local machine decisions more responsive to the current time horizon.
</DESCRIPTION>
