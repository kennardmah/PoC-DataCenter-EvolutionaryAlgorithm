<deadline_aware_local_scheduling>
This change introduces deadline-awareness into the local machine scheduling by calculating a `hard_latest_start_time_for_op`. This time represents the absolute latest an operation can start to ensure the entire job *could* still meet its deadline, assuming subsequent operations run without delay. The search for a local slot is then constrained by this value, effectively narrowing the search window.

**Argumentation:**
The previous scheduler prioritized finding the earliest possible local slot, regardless of whether that slot would ultimately lead to a job missing its deadline. This could result in higher `delay_penalty` costs, especially for high-priority jobs. By integrating deadline-awareness:

1.  **Reduces Delay Penalties**: The scheduler will now only consider local slots that allow the job to potentially meet its deadline. If no such local slot exists, it is more likely to fall back to using cloud resources, which can be scheduled immediately, minimizing delays for critical operations. This directly addresses the `delay_penalty` component of the objective, which has a 5x weight.
2.  **Optimizes Cloud Tradeoff**: The decision to use cloud becomes more strategic. Instead of resorting to cloud only when *no* local capacity is available at all (even if it's too late), cloud is now considered when local capacity isn't available *soon enough* to prevent a deadline miss. This prevents "late local" assignments that are technically valid but practically detrimental to the overall score.
3.  **Maintains Cost Efficiency (where feasible)**: When multiple local slots *can* meet the deadline, the existing cost and resilience-based tie-breaking mechanisms are still applied. This ensures that cheaper, more resilient local resources are utilized when they don't jeopardize deadlines.

The change also includes a pre-calculation for `job_remaining_durations` to make the `hard_latest_start_time_for_op` calculation efficient within the operation loop.
