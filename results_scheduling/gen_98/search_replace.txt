<flexible_local_lookahead>
This improvement refines the selection of local machine slots for operations. Previously, for high-priority jobs, the scheduler would strictly pick the earliest available slot on any local machine, without considering if a slightly later slot on the same or another local machine might be significantly cheaper. For low-priority jobs, a fixed `LOW_PRIORITY_COST_LOOKAHEAD_WINDOW` was used.

This change introduces a `GENERAL_COST_LOOKAHEAD_WINDOW` that applies to all jobs, regardless of priority. When searching for an available local slot, the scheduler will now consider all feasible slots within `earliest_start` and `earliest_start + GENERAL_COST_LOOKAHEAD_WINDOW` for each compatible local server.

The selection of the "best" local slot among these candidates is then determined by a multi-criteria sort order:
1.  **Earliest start time:** This remains the primary objective to minimize delays, especially for high-priority jobs.
2.  **Lowest effective cost:** If multiple slots share the same earliest start time, the one with the lowest compute cost (adjusted by the `same_server_bonus_cost_reduction` if applicable) is preferred. This allows for strategic cost savings.
3.  **Highest remaining capacity:** As a tie-breaker, slots that leave more capacity available on the machine after the operation are preferred. This helps reduce future contention.
4.  **Server ID:** For deterministic tie-breaking.

This approach balances the need for timely job completion (especially for critical tasks) with cost efficiency, allowing for minor, strategically chosen delays to achieve substantial cost reductions without violating hard constraints. It generalizes the cost lookahead mechanism previously only applied to low-priority jobs, providing more nuanced decision-making for all priorities.
