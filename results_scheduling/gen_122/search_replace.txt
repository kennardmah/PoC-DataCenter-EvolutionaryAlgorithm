<DESCRIPTION>
This enhancement integrates a 'capacity contention penalty' directly into the operation's objective value calculation. Previously, capacity awareness was primarily handled by finding the earliest available slot and using minimum free capacity as a tie-breaker. This change proactively discourages over-saturating local machines by adding a penalty to the objective if placing an operation would leave very little remaining capacity.

The penalty is calculated based on how far the minimum projected free capacity during the operation's execution falls below a defined threshold. This incentivizes the scheduler to utilize local resources more judiciously, potentially spreading the load more evenly or opting for cloud resources sooner for less critical jobs or highly contended machine types. This should lead to:
1.  **Improved Resilience**: By avoiding highly contended local slots, the system retains more slack, making it less susceptible to cascading failures or performance degradation, especially in earthquake scenarios where capacity can suddenly drop.
2.  **Reduced Cloud Relocations**: Proactive load balancing on local machines might reduce the need for reactive, costly cloud relocations if local capacity becomes critically low.
3.  **Better Cost-Efficiency**: By incorporating future contention into the decision-making, the scheduler can make more informed trade-offs between immediate low local cost and the implicit future costs of resource contention (delays for other jobs, or eventual cloud migrations).

Two new class attributes, `CAPACITY_PENALTY_THRESHOLD` and `CAPACITY_PENALTY_FACTOR`, are introduced to allow for tuning this new penalty. The penalty is applied only to local servers, as cloud servers have unlimited capacity.
</DESCRIPTION>
