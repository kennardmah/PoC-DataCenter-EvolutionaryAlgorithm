<sequential_scheduling>
Prioritized Sequential Scheduling for Critical Jobs (Immediate Successor Chain)

This enhancement implements "Recommendation 5". For operations belonging to CRITICAL or HIGH priority jobs, if the immediately preceding operation of the same job was scheduled on a local server and the current operation requires the same server type, that specific local server is prioritized.

This prioritization is achieved by:
1.  Tracking the local server used by the previous operation of the same job in `self.last_scheduled_local_server_per_job`.
2.  If the current job is CRITICAL/HIGH priority and the current operation requires the same machine type, the previously used local server is prepended to the `local_servers_for_type` list. This ensures it's checked first for an earliest slot.
3.  Additionally, a `preferred_for_chaining_score` is introduced into the `local_candidates` tuple. This score (0 for preferred, 1 for normal) is used as an additional sorting key. This means that if multiple local servers offer the exact same earliest start time, the one that facilitates sequential chaining of critical jobs will be chosen over others. The lowest cost and highest remaining capacity tie-breakers from previous improvements will still apply among equally preferred/non-preferred servers.
4.  After an operation is scheduled on a local server, `self.last_scheduled_local_server_per_job` is updated for that job. If an operation is scheduled on a cloud server, this state is cleared for the job, as cloud operations don't allow for local chaining.

This strategy aims to reduce internal job delays for critical workloads, improving throughput and potentially leading to earlier completion times, thereby reducing delay penalties. By consolidating critical operations on the same local machine, it can also lead to more efficient resource utilization.
</sequential_scheduling>
